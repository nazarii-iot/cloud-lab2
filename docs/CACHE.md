Кешування операцій читання

Реалізація cache-aside

У REST API реалізовано підхід cache-aside для GET /items та GET /items/{id}. Спільним сховищем кешу є Redis. Час життя кешованих значень, TTL, становить 45 секунд. Під час читання застосунок спочатку перевіряє наявність значення в Redis. Якщо значення відсутнє, дані отримуються з основного сховища, після чого результат записується до кешу.

Після успішного створення нового запису застосунок інвалідовує пов'язані ключі кешу. Це зменшує ризик повернення застарілих даних після зміни вмісту бази.

Хмарне розгортання Redis

В інфраструктурі Terraform описано Amazon ElastiCache replication group з ідентифікатором cloud-lab2-redis. Під час перевірки ресурс мав стан available, тип вузла cache.t4g.micro та порт 6379. Для з'єднання налаштовано шифрування трафіку.

У ECS task definition cloud-lab2-api, revision 6, контейнер API отримує змінну середовища REDIS_URL. Вона визначає адресу та параметри підключення до хмарного Redis. Саме значення підключення не публікується в документації або репозиторії, оскільки може містити конфіденційні параметри.

Доступність Redis перевірялася через endpoint /health/redis. Статистика кешу доступна через /cache/stats. Таким чином, хмарна конфігурація Redis описана окремо від локальних тестів продуктивності.

Змішаний локальний тест

Порівняльні прогони змішаного сценарію виконувалися локально проти http://localhost:8080 з 30 віртуальними користувачами, ramp-up 180 секунд, steady 300 секунд і ramp-down 120 секунд. Сценарій містив як операції запису, так і операції читання. Ці результати характеризують локальний тестовий стенд, а не продуктивність AWS ElastiCache.

Показники без кешу:

Усього запитів — 62 912.
HTTP-помилки — 0.
RPS у steady-фазі — 90,85.
p50 у steady-фазі — 166,80 мс.
p95 у steady-фазі — 351,45 мс.
p99 у steady-фазі — 453,71 мс.

Показники з Redis:

Усього запитів — 33 084.
HTTP-помилки — 0.
RPS у steady-фазі — 53,48.
p50 у steady-фазі — 281,03 мс.
p95 у steady-фазі — 634,59 мс.
p99 у steady-фазі — 801,08 мс.
Cache hit ratio — 27,7%.

У змішаному сценарії p95 збільшився з 351,45 до 634,59 мс, тобто приблизно на 80,6%. RPS зменшився з 90,85 до 53,48. Отже, в цьому профілі навантаження кеш не покращив загальну затримку API.

Причина погіршення змішаного сценарію

Змішаний сценарій містив записи, після яких пов'язані ключі кешу інвалідовувалися. Через це частина результатів читання не могла бути повторно отримана з Redis, а cache hit ratio становив лише 27,7%. Більшість звернень не отримувала вигоди від повторного використання кешованого значення.

Водночас шлях через кеш додає окремі операції: звернення до Redis, передавання даних, серіалізацію та десеріалізацію значень, а також обробку ключів та інвалідації. За низької частки повторних cache hit ці витрати можуть перевищувати економію на зверненнях до PostgreSQL. Саме це узгоджується зі збільшенням p95 у змішаному локальному тесті. Зменшення навантаження на PostgreSQL саме по собі не гарантує зменшення повного часу відповіді API.

Окремий тест повторного читання

Для перевірки сценарію з високою повторюваністю читань виконано окремий локальний прогін із 300 повторними запитами та 20 паралельними працівниками.

Без кешу p95 становив 123,56 мс, пропускна здатність — 215,42 запиту за секунду, cache hit ratio — 0%.

З Redis p95 становив 27,84 мс, пропускна здатність — 804,65 запиту за секунду, cache hit ratio — 100%.

У цьому сценарії Redis зменшив p95 приблизно на 77,5%, а пропускна здатність зросла приблизно у 3,74 раза. Результат відрізняється від змішаного тесту, оскільки ті самі дані читалися багаторазово, а отже кеш мав змогу повертати вже збережені значення без повторного звернення до PostgreSQL.

Актуальність даних і TTL

TTL 45 секунд обмежує час зберігання кешованого значення. Після успішного створення запису застосунок інвалідовує пов'язані ключі, щоб наступне читання отримало актуальні дані з бази та оновило кеш. Якщо інвалідація не відбудеться, TTL обмежує максимальний час життя такого значення в кеші приблизно 45 секундами.

Висновок

Ефективність кешування залежить від повторюваності читань і частоти операцій запису, які інвалідовують ключі. У змішаному локальному сценарії частка повторних cache hit була недостатньою, щоб компенсувати додаткові витрати Redis, тому p95 погіршився. У сценарії повторного читання тих самих даних кеш забезпечив 100% cache hit і суттєво зменшив затримку. Ці локальні результати демонструють залежність ефекту від профілю навантаження, але не є прямим порівнянням продуктивності локального Redis та AWS ElastiCache.
