Підсумок лабораторної роботи 2

Мета роботи

Метою роботи було розгорнути REST-сервіс в AWS, налаштувати автоматичне масштабування ECS, зібрати метрики в CloudWatch, налаштувати повідомлення SNS та додати Redis-кешування для операцій читання.

Реалізована інфраструктура

REST API розгорнуто як контейнеризований сервіс у ECS Fargate. Вхідний трафік надходить через Application Load Balancer. Для зберігання даних використовується RDS PostgreSQL. Для кешування передбачено Amazon ElastiCache for Redis. Інфраструктура описана Terraform.

Для ECS налаштовано автоматичне масштабування в межах від 1 до 4 tasks за метрикою ALBRequestCountPerTarget. Цільове значення становить 80 запитів на target за хвилину. CloudWatch Dashboard містить метрики ECS, ALB, Redis та RDS. CloudWatch alarms надсилають повідомлення через SNS під час переходів між станами ALARM та OK.

Результат хмарного навантажувального тесту

Під час тесту було виконано 4209 HTTP-запитів протягом 598,58 секунди. Було зареєстровано 0 HTTP-помилок. Середня інтенсивність становила 7,03 запиту за секунду.

Клієнтська затримка: p50 — 77 мс; p95 — 10074,05 мс; p99 — 11081,8 мс; максимальна затримка — 21073,38 мс.

Таким чином, тест не виявив HTTP-помилок, але показав значну затримку для повільнішої частини запитів. p95 дорівнює приблизно 10,07 секунди, а приблизно 21,07 секунди — це максимальна затримка окремого запиту, а не p95. Ці показники не слід ототожнювати.

Масштабування та сповіщення

Під час тесту DesiredTaskCount досяг максимального значення 4 о 02:22:14 за київським часом. Після завершення тесту масштабування вниз відбувалося поступово. Кількість tasks зменшилася до 3 о 02:44:38, до 2 о 02:48:38 та до 1 о 02:52:38. Після цього сервіс мав Desired 1, Running 1, Pending 0.

Повідомлення SNS про перехід alarm у стан OK має часову позначку 02:46:33 за київським часом. Це сталося після зменшення DesiredTaskCount нижче порога 4, коли значення становило 3. Повідомлення OK не означало, що сервіс уже повернувся до однієї task. До мінімальної кількості 1 task сервіс повернувся о 02:52:38.

Результати кешування

У локальному змішаному сценарії p95 збільшився з 351,45 мс без кешу до 634,59 мс із Redis. Частка cache hit становила 27,7%, тому більшість операцій не отримала переваги повторного читання з кешу, а додаткові операції Redis збільшили загальну затримку.

У локальному сценарії повторного читання тих самих даних p95 зменшився зі 123,56 мс до 27,84 мс, пропускна здатність зросла з 215,42 до 804,65 запиту за секунду, а частка cache hit досягла 100%. Це показує залежність ефекту кешу від профілю доступу до даних.

Висновок

У межах лабораторної реалізовано інфраструктуру REST-сервісу, масштабування ECS, моніторинг CloudWatch, сповіщення SNS і кешування Redis. Вимірювання зафіксували як успішне масштабування та відсутність HTTP-помилок у тестовому прогоні, так і проблему високих клієнтських p95 та p99. Кешування покращило сценарій повторного читання, але погіршило змішаний локальний сценарій із невеликою часткою повторних cache hit. Це підтверджує, що налаштування кешу та масштабування потрібно оцінювати за конкретним профілем навантаження, а не лише за фактом наявності відповідних компонентів.
